# Design: /junior learning loop — ask first, explain only the gaps

Generated by /office-hours on 2026-10-22
Branch: dev
Repo: stefanwuthrich/junior-skill
Status: APPROVED
Mode: Startup (intrapreneurship)

## Problem Statement

Developers on the team, juniors especially, ship working PRs that Claude wrote but cannot explain why the code is shaped that way or what breaks if it changes. Nobody checks, so the gap compounds after every merge. The current `/junior` produces a passive six-section explainer that early users skim and close. It never asks them to produce an answer.

## Demand Evidence

- Observed failure: authors can't explain their own AI-written PRs in review.
- Observed workaround: "we merge anyway". Deadlines win and nobody follows up.
- Observed usage of `/junior` today: "skimmed and moved on". Concepts, links and the "Try this" exercise are skipped.
- External evidence: Anthropic's 2026 randomized trial (52 mostly junior devs). The AI-assisted group scored 50% on a comprehension quiz, the group without AI scored 67%. The largest gap was on debugging questions. Devs who asked conceptual "why" questions scored 65% or more; devs who handed off code generation scored under 40% ([InfoQ, 2026-02](https://infoq.com/news/2026/02/ai-coding-skill-formation/); secondary coverage, read the primary report before quoting numbers externally).
- Gap: no named individuals yet. Demand is inferred from observed behavior, not from someone asking for this feature.

## Status Quo

1. A dev builds with Claude Code, accepts the result, and opens a PR.
2. The reviewer sees working code and merges, even when the author can't explain it.
3. `/junior` is opt-in and passive. When someone runs it, they skim it.

Cost: understanding never forms, and debugging skill (the biggest measured gap) never develops. It shows up later, when the AI is wrong or a production bug needs a human mental model.

## Target User & Narrowest Wedge

- Primary: juniors on the team checking their own AI-written work before or after a PR.
- Secondary ("not only juniors"): reviewers who want to check understanding without writing questions themselves, and seniors entering an unfamiliar part of the codebase.
- Wedge: the quiz on your own diff (`/junior` default). The other modes reuse the same quiz engine.

## Constraints

- Ships as one prompt file. Source: `JUNIOR-SKILL.md`; installed as `SKILL.md` with a `name` field via the README build steps (`README.md:28-33`, `:63-64`). No runtime, no backend, no dependencies.
- Must work on claude.ai (no git, no persistent filesystem; user pastes the diff) and in Claude Code (runs git, can write files).
- Keep all four languages: en, pt (pt-BR), sr (Latin; `sr-cyrl` for Cyrillic), de.
- Public repo: the log must never contain secrets or code. It stores concept names only.
- Don't rebuild the "learn while coding" mode. Claude Code's built-in Learning output style (`/config` → Output style → Learning, with `TODO(human)` gaps) covers it.

## Premises

1. The problem isn't missing explanations. Nobody checks whether the author understood, so the gap compounds after merge.
2. Passive explanation gets skimmed (observed). Learning happens when the person has to produce an answer: explain-back, predict, debug.
3. `/junior` flips from "explain everything" to "ask first, explain only the gaps". The six-section walkthrough stays available as `explain`.
4. Don't rebuild learn-while-coding; point to the built-in Learning output style.
5. The same quiz serves juniors, reviewers and seniors new to an area. Difficulty adapts; the mechanism stays the same.

## Approaches Considered

### Approach A: Quiz-first /junior (minimal)
Default becomes a 3-question explain-back on the diff, `explain` keeps the old walkthrough. S effort. Not chosen: the user wanted reviewer and onboarding coverage from the start, matching "not only juniors".

### Approach B: Learning loop (CHOSEN)
A, plus `review` and `onboard` modes and a per-user log of missed concepts that later quizzes revisit.

### Approach C: Questions live in the PR
The reviewer posts generated questions as PR comments via `gh`, and the author answers before merge. Deferred, not rejected: it is the follow-up if opt-in usage of B stays low. "Merge anyway" is the risk B doesn't address.

## Recommended Approach

**Approach B, still in a single `JUNIOR-SKILL.md`.** The modes share one quiz engine described once in the prompt.

### Argument grammar

`/junior [mode] [scope] [lang] [nolog]`, in any order, as today.

| Mode | Who | Input | Output |
|---|---|---|---|
| `quiz` (default) | Author | Diff scope (same rules as today: uncommitted, else last commit, or explicit ref/range/PR) | 3 questions, one at a time, graded; explanations only for gaps; understanding note |
| `explain` | Anyone | Diff scope | Today's six-section walkthrough, unchanged |
| `review` | Reviewer | Ref/range/PR | 3 questions to ask the author, each with an answer key (what a good answer must mention). Prints only, never posts. |
| `onboard <path>` | Senior or anyone new to an area | A file or directory instead of a diff | 3 prediction questions about how that code behaves; graded; gaps explained |

Mode words are reserved: `quiz`, `explain`, `review`, `onboard`. Anything else is parsed as scope/lang as today. Bare `/junior` = `quiz` on the default scope.

Parse rules:
- **One mode at most.** If two mode words appear (e.g. `quiz review`), stop and ask which one; don't guess.
- **`onboard` takes the next token as its path, literally**, even if that token is also a mode word, language code or ref (`/junior onboard review` = onboard the `review` directory). In Claude Code the path must exist; if it doesn't, say so and ask. On claude.ai there's no filesystem: `onboard` asks the user to paste the code instead.
- **`review` with no scope** defaults to the current branch against the repo's default branch (`git symbolic-ref --short refs/remotes/origin/HEAD`, falling back to `main`, then `master`), i.e. `<base>..HEAD`, and names the base it used (eng-review D2). If that range is empty (only uncommitted changes, or on the default branch), say `review` is for committed work and suggest `quiz` instead. Uncommitted changes are never the default for `review`.
- **`nolog`** only affects `quiz` and `onboard`. With `review` or `explain` it's accepted and ignored, since those modes never touch the log.

**Behavior change for existing users:** bare `/junior` no longer prints the walkthrough. The README says so, and the first line of quiz output says "want the full walkthrough instead? run `/junior explain`".

### Quiz engine (shared by quiz and onboard)

1. **Pick 3 questions from the diff/code**, one of each type, each anchored to a real file/function:
   - **Why**: "Why is X shaped this way rather than the obvious alternative?"
   - **Break**: a debugging or prediction scenario. "What happens if Y is nil / this runs twice / the call times out?" (targets the largest measured gap)
   - **Alt**: "Why not do Z instead?" (trade-off judgment)
   Skip boilerplate; pick decisions. For tiny diffs with fewer than 3 real decisions, ask fewer and say why.
2. **Ask one at a time.** Wait for the answer. Never show the next question, or any answer, before the user replies. "skip" / "I don't know" is allowed, without judgment: shown to the user as missed, logged as `skipped`.
3. **Grade each answer**: shown to the user as `got it` / `partial` / `missed`, with one sentence on what was right. Logged as `got-it` / `partial` / `missed` / `skipped` (see Learning log).
4. **Explain only the gap.** For partial/missed: name the concept (searchable term), explain it briefly against the actual code, and give at most 2 links (official docs first). For got it: one line of confirmation, no lecture.
5. **Adapt difficulty** (eng-review D4). Order is fixed: Why -> Break -> Alt. After each answer, set the next question's level: `got it` -> harder (edge case, cross-file interaction, concurrency); `partial` -> same level; `missed` -> more concrete (one function, one input). Applies to questions 2 and 3. Tiny diffs with fewer than 3 real decisions drop Alt first, then Why; Break is always kept. A diff with zero decisions (pure rename/formatting): say there's nothing to quiz and offer `/junior explain`. This is how one mechanism serves juniors and seniors without a `--level` flag.
6. **Close** with:
   - Score line (e.g. `2/3 — missed: idempotency`).
   - **Understanding note**: 2-3 sentences in the author's words, reconstructed from their answers (not Claude's), ready to paste into the PR description. Wording: "Based on your answers:". If they missed everything, there's no note; suggest `/junior explain` instead.
   - One line pointing to the Learning output style for learning *during* the next task.

Honesty rule (carried over from today): never fabricate rationale. If the diff doesn't show why something was done, the question must not assume a reason; ask the user what they think instead.

### Review mode

Same question selection, but output is a list for the reviewer: question, file anchor, and an answer key with 2-3 points a good answer must cover. It does not grade and does not post anywhere (posting is Approach C). Language follows the `lang` argument.

### Learning log (spaced retrieval)

- **Where**: `~/.junior/log.md` (created on first write), one per user, across repos. Not inside the repo, so there's nothing to git-ignore and no risk of committing it. Claude Code asks permission for writes outside the project, so the README documents a one-time allow rule for Write/Edit on `~/.junior/**`; a denied write is reported in one line and the quiz continues (eng-review D1). Claude Code only. On claude.ai, the close instead lists the missed concepts and says the log isn't available there.
- **What**: one line per graded question: `YYYY-MM-DD | repo | mode | concept | grade`. `repo` is the working directory's basename only (no path, no remote URL). `mode` is `quiz`, `onboard` or `warmup`. `grade` is `got-it`, `partial`, `missed` or `skipped` (an explicit skip or "I don't know"; scored like missed but kept separate so a fully answered quiz can be told apart). Concept names only, never code, never file contents.
- **Concept names**: lowercase kebab-case slug, at most 40 characters, `a-z0-9-` only (e.g. `idempotency`, `optimistic-locking`). Before writing a new slug, read the existing slugs in the log and **reuse one that names the same concept** instead of inventing a synonym. Matching is best effort: a concept logged under two slugs is revisited twice, which costs one extra question and is acceptable.
- **Open concept**: a slug whose **most recent** line is `partial`, `missed` or `skipped`. Age = today's date (from the system, not guessed) minus that line's date.
- **Revisit (warm-up)**: at the start of a `quiz` or `onboard` run, read the log. If any open concept is at least 3 days old, pick the oldest and ask **one** warm-up question about it before the main questions. Max one warm-up per run, whatever repo or mode the concept came from.
  - **Construction**: concept-only by default ("what problem does idempotency solve, and what's one way it fails?"). Only anchor it to current code if the concept visibly appears in the current diff or path. Never refer to code from another repo or an earlier session that isn't in context.
  - **Logging**: write the warm-up as a `warmup` line with its grade. `got-it` closes the concept. `partial`/`missed`/`skipped` keep it open with today's date, so it comes back no sooner than 3 days later.
  - **Score**: the warm-up isn't counted in the main score line; it's reported on its own line (`warm-up: idempotency — got it`).
- **Size**: the log is scanned in full. When it passes 400 lines (eng-review D7), drop the oldest lines on the next write, keeping the newest 400, but never drop the latest line of a slug that is still open (pruning must not silently close a concept).
- **Opt-out**: `nolog` skips reading and writing. If the file can't be written, say so in one line and continue; the quiz never fails because of the log.
- **No log in `review` mode**: the reviewer isn't the learner.

### What stays the same

Scope resolution rules, language rules (including keeping technical terms as-is), the honesty rule, tone section, and the `explain` output structure.

## Open Questions

1. Will people resent being quizzed by default, or skip it the way they skipped the explainer? Only the assignment and dogfooding answer this. Reverting the default to `explain` is a one-line change.
2. Is grading reliable in de/sr/pt? Free-text answers in a second language may be judged harshly. Watch for it in dogfooding.
3. Is a 3-day revisit interval right? It's a guess. Tune after two weeks of log data.
4. If opt-in usage stays low after two weeks, adopt Approach C (questions in the PR) as a team norm.

## Success Criteria

Cohort: the early users who already tried `/junior` (write their names down when doing the assignment). Window: the first two weeks after release, ending in a 15-minute check-in with each of them.

| Criterion | Target | How it's measured |
|---|---|---|
| Completed quizzes | ≥2 people complete a quiz on their own work on ≥2 separate days | Claude Code users: count `quiz` log runs on distinct dates where every asked main question (fewer than 3 on tiny diffs) has a grade other than `skipped` (they share counts at the check-in, not the file). claude.ai or `nolog` users: self-report at the check-in. |
| Spaced retrieval works | ≥1 concept closes via a `warmup` line graded `got-it` | Log, Claude Code users only; best effort given slug matching |
| Reviewer adoption | ≥1 reviewer uses `review` questions in a real PR review | Self-report at the check-in, plus a link to the PR thread |
| Understanding | An author who ran the quiz answers a "what breaks if" question about their PR in review | You ask it in a real review and note the answer |

If the completed-quiz criterion fails, revisit Open Question 1 (default mode) and Approach C before anything else.
